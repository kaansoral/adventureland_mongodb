Game and CODE architecture

Each character has two cooperating browser contexts:

Game frame Owns the server socket, live entities, map state, rendering, CODE editor, and account API calls CODE frame (/runner) Loads the public CODE functions, event listeners, compatibility helpers, and your code

The CODE frame is deliberately separate. Restarting CODE replaces that frame and clears ordinary JavaScript variables, timers, listeners, and unfinished work from the old run. The game frame and character connection stay alive.

How an action travels

Your code -> public function such as attack(target) -> game frame registers the pending response -> socket request reaches the game server -> socket response reaches the game frame -> the matching Promise fulfills or rejects in your CODE frame

The response is registered before the request is sent. Requests sharing a response channel are queued in request order. Use the public functions instead of raw socket emits so matching replies, safeguards, timeouts, and compatibility behavior remain intact.

Live data

character, nearby entities returned by functions such as get_entity, and the objects under parent are live runtime objects. Do not keep a nearby entity reference forever: an entity that leaves visibility stops updating. Fetch it again by ID or name when needed.

G contains game definitions such as items, skills, maps, monsters, and recipes. Definitions describe content; the server decides whether an action is valid and what it finally costs or changes.

Events

character.on("loot", function (data) { show_json(data); }); game.on("hit", function (data) { // World event: may describe another entity. });

Socket data is normalized by the game frame and forwarded to character or game listeners in the CODE frame. Character events concern your character; game events describe the visible world or server. See both event references for exact event data.

Account API

parent.api_call sends an HTTP request to the account/backend API. It is separate from real-time character socket actions. Public wrappers such as upload_code should be preferred when one exists.

Multiple characters

start_character opens another owned character with its own game frame, socket, CODE frame, variables, and listeners. Communicate through send_cm; do not assume two characters share JavaScript memory merely because they are open in the same browser.

Persistence boundaries

set("local-plan", { monster: "goo" }); // Browser-local JSON value pset("raw-key", "raw value"); // Platform persistent string upload_code(12, "helpers", source); // Account-backed code slot; returns a Promise

Choose storage deliberately. Ordinary variables last only for the current CODE run; get/set and pget/pset are local to the current platform profile; code slots are stored with the account.
