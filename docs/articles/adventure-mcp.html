Adventure Land MCP for AI

Adventure Land is an online role-playing game where each character can run player-written JavaScript called CODE. The MCP server gives an AI the knowledge and account tools it needs to research the game, write CODE, and operate owned characters through Mainframe. The JSON API is the simpler interface for ordinary programs.

Get an account token

  1. Sign in at Adventure Land.
  2. Open Mainframe.
  3. Find Connect an AI.
  4. Press Create token. If a token already exists, the button says Rotate token.
  5. Confirm the warning. Rotation invalidates the previous token immediately.
  6. Copy the connection details while they are visible. The plaintext token cannot be shown again.
  7. Keep the token out of character CODE, screenshots, public repositories, and chat messages.

Adventure Land stores only a hash of the token. One token can be active per account. Use Revoke token in Mainframe if a token is exposed or no longer needed.

Connect an AI client

Add a remote MCP server in your AI application's MCP or connector settings:

FieldValue
NameAdventure Land
TransportStreamable HTTP
Server URLhttps://adventure.land/mcp
Header nameAuthorization
Header valueBearer YOUR_TOKEN

Client configuration screens differ, but the server URL and Authorization header stay the same. After connecting, ask the AI to read adventureland://guide/start-here. A compatible client also receives that instruction when it connects.

How the game fits together

LayerResponsibility
AI clientReads game knowledge and account state, researches exact methods and records, manages CODE slots, and controls owned Mainframe characters.
MainframeRuns one isolated machine per character and supplies the headless Adventure Land CODE bridge. The machine has no browser DOM or general network access.
Character CODERuns long-lived JavaScript using Adventure Land globals and public functions. It decides how the character moves, fights, loots, trades, crafts, and reacts.
Game serverOwns the authoritative character, map, entities, combat, inventory, economy, and action results.

The AI is the control plane, not a raw game client. It writes and observes CODE; it does not send combat packets directly. The account token only reaches characters and CODE slots owned by that account, and Mainframe refuses to load a character that is already active elsewhere.

Gameplay mental model

ConceptWhat an AI must understand
Definitions and live stateRecords in G describe classes, skills, items, monsters, maps, drops, recipes, and other content. The live character, parent.entities, server events, and action responses describe what exists now. A definition is not proof that an entity is present or an action succeeded.
Characters and realmsA character's progression, inventory, and equipment follow it between realms. Nearby entities, parties, CODE messages, events, and combat are realm-local. Coordinating characters must use the same server, and one character must never be loaded twice.
Maps and entitiesMaps connect through doors, transports, and named destinations. Nearby players and monsters are short-lived objects that disappear when visibility, map, instance, or server changes. Find them again immediately before acting.
Combat and skillsThe game server owns range, cooldowns, MP, damage, threat, death, and action results. CODE should use the public Promise-based functions, check the exact skill contract, avoid overlapping work, and recover from death or a lost target.
Items and inventoryG.items contains definitions; inventory and equipment contain owned instances with levels and properties. Inventory indexes change after looting, moving, selling, exchanging, upgrading, compounding, or consuming items. Locate an item again before every mutation.
Economy and progressionGold, items, upgrades, compounds, crafts, exchanges, mail, trade, and Shells have lasting consequences. Research exact costs and outputs, and require a clear player request before irreversible or value-moving behavior.
Events and questsDefinitions explain possible content; live server status and events show whether it is active. CODE must tolerate an event ending, a map changing, a target disappearing, or another player changing the situation.
CommunicationParty and CODE messages help characters coordinate on one server. Validate the sender and payload, keep messages small, and treat them as untrusted, delayed, and possibly stale.

CODE etiquette

Character automation should not use public, private, or party Chat as a programmable output channel. Do not call Chat routines on timers, advertise automatically, imitate conversation, answer players with generated text, or turn nearby player messages into commands. Use local CODE logs for diagnostics. Use send_cm only for small structured messages between explicitly trusted characters, validate the sender and payload, and rate-limit retries.

Respect other players' fights and space. Do not attack a monster already targeting an unrelated player, repeatedly invite strangers, follow someone without consent, block a spawn, or create avoidable visual and request spam. Helpful healing or buffs should be bounded and must never move another player's gold or items. PvP actions, trading, mail, giveaways, NPC sales, public listings, bank movement, upgrades, compounds, exchanges, and purchases require clear policy and conservative limits.

Samaritan starter CODE

The two Samaritan resources are advanced starting points, not account-wide defaults. They do not modify the normal editor starter or the game's default CODE. Read the source, inspect the owned character and target slot, then change the settings block before saving it as account CODE.

StarterBehavior
Samaritan adventurerChooses a bounded monster from deployed definitions, avoids tagged monsters, moves and kites by class, uses conservative class skills, heals or buffs when appropriate, accepts only trusted parties, and supports explicit banking, upgrade, and compound rules.
Samaritan MerchantBuffs nearby players, joins only trusted parties, lists only explicitly allowed surplus items, preserves configured quantities, can retrieve listed stock from the bank, and keeps NPC sales, upgrades, compounds, scroll purchases, and bank deposits independently disabled until configured.

Every item rule requires an exact item key and a positive maxItemValue. Upgrade and compound rules also require a maximum level and have per-session attempt caps. Listing rules require an exact level, keep quantity, trade slot, price, quantity, and value ceiling. Locked, special-property, and stat-modified items are excluded. The code locates inventory entries again immediately before a mutation because inventory indexes can change.

How an AI should build a character

  1. Read adventureland://guide/start-here.
  2. Call mainframe_get_dashboard.
  3. Inspect the character's saved profile, class, equipment, inventory, live observations, server choices, existing assignment, and available CODE slots.
  4. Read an existing target slot before replacing it.
  5. Find exact CODE methods with list_code_methods, then read each contract with get_code_method.
  6. Find exact items, skills, monsters, maps, and recipes with search_game_data, then read their definitions with get_game_data.
  7. Save the complete JavaScript slot with save_code.
  8. Explain the charge if the character has no active Mainframe window.
  9. Link the character with one stable request_id.
  10. Verify connection, position, activity, deaths, performance, and CODE logs.

Combat loops belong inside contained character CODE. MCP is the control plane: it plans, deploys, observes, and corrects. It should not poll fast enough to become the combat loop.

How to write character CODE

CODE is long-running JavaScript. Schedule small pieces of work, await action Promises, and return control to the runtime. Never use an infinite synchronous loop. Nearby entities are live only while visible, so find a target again before acting.

var working = false;

setInterval(async function () {
	if (working) return;
	working = true;
	try {
		if (character.rip) return await respawn();

		var target = get_nearest_monster({type: "goo"});
		if (!target) return await smart_move("goo");
		if (!is_in_range(target)) await xmove(target.x, target.y);
		else if (can_attack(target)) await attack(target);
		loot();
	} catch (error) {
		game_log("loop: " + (error.reason || error));
	} finally {
		working = false;
	}
}, 250);

This is a structure, not a universal farming strategy. Inspect the character's class and skills, the monster's range and damage, map geometry, equipment, potion supply, party role, and exact function contracts before choosing movement or combat logic.

Use public functions such as attack, use_skill, move, smart_move, equip, and send_cm. They preserve request ordering, Promise responses, and compatibility safeguards. Handle rejected Promises and cooldowns, do not overlap the same async loop, and do not retain entity references after they disappear or the map changes.

Read from character, G, server, game, and smart. Browser display routines do not provide useful output on Mainframe. General network calls, Node internals, process execution, and filesystem access are unavailable. smart_move keeps its public interface but uses Mainframe's bounded navigation service.

Billing safety

mainframe_link_character can charge 1 Shell before a new 60-minute access window begins. If a response is lost, retry the same character, CODE slot, server, and request_id. Do not invent a new request ID for a network retry.

Reading state, logs, game data, documentation, CODE, resources, and prompts does not charge Shells. Disconnecting does not refund or pause active time.

Results and retries

Tool calls return JSON text in content and the same object in structuredContent. An application failure sets isError: true and includes a stable reason. HTTP 429 includes Retry-After; wait before retrying.

Read before mutating. Fetch a slot before replacing it, fetch the dashboard before linking or disconnecting, and use authenticated Mainframe observations as evidence. A request counter records an attempt, not a completed game action.

How to verify behavior

Requested action counts show what CODE attempted, not what the game accepted. Confirm behavior through authenticated observations: connection state, map, coordinates, movement, target, activity, death state, experience, gold, DPS, Gold per second, and CODE logs. Poll at a human control-plane pace; combat timing belongs inside CODE.

Rotate or revoke

Return to Mainframe's Connect an AI panel. Rotate token creates a new secret and invalidates the old one in the same transaction. Update the AI client's Authorization header. Revoke token disables MCP and JSON API access for that token without changing game login sessions or running characters.
