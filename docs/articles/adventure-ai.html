Adventure Land for AI

Adventure Land is an online role-playing game where each character can run player-written JavaScript called CODE. An AI does not send combat packets directly. It researches the game, writes or updates an account-owned CODE slot, and can run that slot for an owned character through Mainframe.

The four layers

AI client Connects to https://adventure.land/mcp Reads game knowledge and account state Reads or saves CODE slots Starts, stops, and observes owned Mainframe characters Mainframe Runs one isolated machine per character Supplies the headless CODE runtime and Adventure Land bridge Has no general internet access or browser DOM Character CODE Runs normal JavaScript with Adventure Land globals and public functions Decides how the character moves, fights, loots, trades, crafts, and reacts Game server Owns the authoritative character, map, entities, combat, inventory, economy, and action results

The MCP account token only reaches characters and CODE slots owned by that account. Mainframe refuses to load a character that is already active elsewhere. An AI cannot use MCP as a raw character socket or bypass ordinary game validation.

What the AI should read first

The MCP resource adventureland://guide/start-here contains this guide. The server also exposes resources for the CODE runtime, architecture, globals, character and monster objects, events, Mainframe, the complete shipped runner source, live servers, owned slots, and the account dashboard.

For a specific task, the AI should use:

list_docs / get_doc Game rules, CODE architecture, objects, events, movement, items, and skills list_code_methods / get_code_method Exact function signatures, Promise behavior, examples, failures, and source locations search_game_data / get_game_data Exact items, skills, monsters, maps, classes, recipes, conditions, events, and NPCs list_codes / get_code Account-owned CODE slots and their current source mainframe_get_dashboard / mainframe_get_character / mainframe_get_logs Owned characters, assignments, paid access, confirmed game observations, and CODE output

How to write character CODE

CODE is long-running JavaScript. It should schedule small pieces of work, wait for action Promises, and return control to the runtime. It must not use an infinite synchronous loop. Nearby entities are live only while visible, so find the target again before acting.

var working = false; setInterval(async function () { if (working) return; working = true; try { if (character.rip) { await respawn(); return; } var target = get_nearest_monster({type: "goo"}); if (!target) { await smart_move("goo"); return; } if (!is_in_range(target)) { await xmove(target.x, target.y); } else if (can_attack(target)) { await attack(target); } loot(); } catch (error) { game_log("loop: " + (error.reason || error)); } finally { working = false; } }, 250);

This is a shape, not a universal farming strategy. The AI must inspect the character's class and skills, the monster's range and damage, the map geometry, equipment, potion supply, party role, and the exact function contracts before choosing movement or combat logic.

Important CODE rules

Use public functions such as attack, use_skill, move, smart_move, equip, and send_cm. They register Promise responses, preserve request ordering, and apply compatibility safeguards. Raw socket emits are for advanced event listening and do not provide those guarantees.

Read from character, G, server, game, and smart. Treat game definitions as descriptive inputs; the server decides whether an action succeeds. Handle rejected Promises and cooldowns. Do not overlap the same async loop. Do not keep entity references after they disappear or the map changes.

Browser display calls are not useful on Mainframe. Buttons, drawings, focus, and other display-only routines are harmless headless operations. General network calls, Node internals, process execution, and filesystem access are not part of character CODE. smart_move keeps its public interface but uses Mainframe's bounded navigation service.

From plan to a running character

1. Read mainframe_get_dashboard. 2. Choose an owned character, live server, and a free or explicitly selected CODE slot. 3. If the slot exists, read it before proposing a replacement. 4. Research every public function and game definition used by the plan. 5. Save the complete CODE with save_code. 6. Explain any new Mainframe charge before starting. 7. Call mainframe_link_character with one stable request_id. 8. Read mainframe_get_character and mainframe_get_logs after the character connects. 9. Judge behavior from authenticated map, position, activity, deaths, performance, and logs. 10. To revise a running assignment: disconnect, save the corrected slot, then reconnect. Active paid time continues.

A new Mainframe window costs 1 Shell for 60 minutes. Reconnecting the same character during its active window does not charge again. Disconnecting does not pause or refund the window. Reuse the same request_id only when retrying the same lost link request; a new ID represents a new request.

How to verify behavior

Requested action counts show what CODE attempted, not what the game accepted. Confirm work through the runtime's authenticated observation: connection state, map, coordinates, movement, target, activity, death state, experience, gold, DPS, Gold per second, and CODE logs. Poll at a human control-plane pace. Combat timing belongs inside CODE, not in repeated MCP calls.
